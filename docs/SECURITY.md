# Security notes

This document is written around what the code actually does, not what one would like it to
claim. Where something is only asserted rather than proven by tests, it is marked.

## Threat model

Three distinct parties:

1. **The desktop user** — a legitimate user on one Windows machine.
2. **The administrator** — controls the shared access password and session revocation.
3. **An attacker** — knows the Worker URL, sits on the same network, or has access to a
   Windows machine where the app was previously run.

The Worker authenticates only. It is deliberately not a control plane, not a data plane,
not a voice relay, and exposes no command execution.

---

## Shared access password

- Never stored in plaintext anywhere: not in the Worker, not in D1, not in a config file,
  not in the repository, not on the desktop.
- Stored in D1 as an **Argon2id PHC string** (`m=19456, t=2, p=1`, 16-byte salt,
  32-byte digest). Proven by `tests/password.test.ts` — the hash never contains the
  plaintext, and each call produces a distinct salt.
- Initially seeded via `wrangler secret put ADMIN_PASSWORD_HASH`, generated by
  `scripts/gen-password-hash.mjs`. No default password exists in the code and the code
  does not ship one.
- Changing the password via `POST /api/admin/change-password` also **revokes every other
  session**, so the old password grants nothing after rotation.
  Proven by `tests/api.test.ts`.
- Minimum 8 and maximum 256 characters, enforced server-side.
  Proven by `tests/api.test.ts`.

## Sessions and tokens

- Access tokens and refresh tokens are 256-bit random values, base64url.
  Only their **SHA-256 hashes** are stored in D1. A database leak does not yield usable
  tokens. The `sessions` columns are literally `token_hash` and `refresh_hash`.
- Access token TTL default **900 s**; refresh token TTL default **7 days**, both
  configurable through `vars`.
- **Refresh rotation**: each `POST /api/auth/refresh` invalidates the previous refresh
  token, so a captured refresh token is single-use.
  Proven by `tests/api.test.ts` ("refresh rotates both tokens and invalidates the old").
- `DELETE` / `POST /api/auth/logout` revokes a session by hash.
  Proven by `tests/api.test.ts`.
- Expired, revoked, and forged tokens all return 401 with a distinct error code.
  Proven by `tests/api.test.ts`.
- `GET /api/auth/validate` rotates the access token on each call, which means the desktop
  client holds a moving session that cannot be replayed long-term. The refresh token is
  preserved by the client, never returned by the Worker.

## Administrator step-up authorization

- A valid session alone is **not** an administrator credential. `GET /api/admin/status`,
  `POST /api/admin/change-password`, and `POST /api/admin/revoke-access` additionally
  require the **current** shared password, sent in the `X-Admin-Password` header or as
  `current_password` in the JSON body (`password` is reserved for the new value).
  Otherwise every machine holding the shared password would be an implicit admin and
  could silently rotate or revoke credentials for everyone else.
  Proven by `tests/api.test.ts` ("status requires the current shared password",
  "change-password rejects a session without password proof",
  "change-password rejects a wrong password proof",
  "revoke-access rejects a session without password proof").
- Admin routes are rate limited separately (`20/min` per caller), because they are the
  most valuable target for an attacker who has stolen a session token.

## Rate limiting

- Sliding window in D1. Keyed by `"<scope>:<sha256(identifier)>"`, so D1 never holds a
  raw caller IP. Proven by `tests/password.test.ts` ("never stores the raw identifier").
- Scopes: `login` 10/min (env-tunable), `refresh` 30/min, `validate` 60/min,
  `admin` 20/min. `refresh` and `validate` are limited because they are the cheapest
  way to burn quota and to replay a stolen token.
- Applies before password verification on `login`, so brute force and timing attacks are
  both throttled. Proven by `tests/api.test.ts` ("rate limit message does not reveal whether
  the password was right").

## CORS

- Explicit allowlist from `ALLOWED_ORIGINS`. A foreign `Origin` receives no CORS header,
  and preflight returns 403.
  Proven by `tests/api.test.ts` (cors block).
- The desktop client sends no `Origin`; non-browser requests are not subject to CORS by
  definition. No wildcard-with-credentials is ever emitted.

## Desktop local secrets

- Stored with **Windows DPAPI**, `DataProtectionScope.CurrentUser`.
- Blob location: `%LOCALAPPDATA%\TeamSer\secrets.bin`.
- Application-scope entropy (`entropy.bin`) is itself DPAPI-protected, so no plaintext
  secret and no static plaintext entropy file sits on disk.
- The ServerQuery password and the auth session live in that blob.
  Proven by `tests/SecureCredentialStoreTests.cs` ("Session is never written to disk in
  plaintext", "QueryPassword roundtrips and is obfuscated on disk").
- A corrupt or foreign-cryptographic blob is treated as absent rather than crashing the
  app. Proven by the same file.

## Process handling

- The app acts only on a process whose **exact full executable path** matches the
  configured directory. It never matches or kills by process name.
  Proven by `tests/ProcessManagementTests.cs` ("Unrelated process is never matched").
- Duplicate start prevention is by process identity, not by guesswork:
  re-running Start against an already-running process returns the same PID instead of
  spawning a second one. Proven by
  `Start_twice_does_not_create_duplicate_process`.
- Graceful shutdown is Ctrl+C equivalent via `GenerateConsoleCtrlEvent`, the mechanism the
  server expects. Forced `.Kill(entireProcessTree: false)` is a last resort after a
  grace window, and is scoped to that single process.
  Proven by `Stop_forces_termination_when_process_ignores_graceful`.
- Crash detection flips state to `Offline` when the managed process exits.
  Proven by `Crash_is_detected_as_offline`.
- Missing or invalid executable paths are reported, not acted on.
  Proven by `Missing_directory_is_reported`, `Directory_without_exe_is_reported`.

## ServerQuery protocol

- Values are escaped per the documented ServerQuery escaping rules before being placed in
  a command. A password containing a space, newline, pipe, backslash or slash cannot
  inject extra parameters or an extra command.
  Proven by `tests/ServerQueryParserTests.cs`
  (`Escape_neutralises_argument_injection`, `Values_with_equals_are_preserved`,
  `Multiple_replies_are_all_parsed`).
- Malformed or truncated replies are reported as errors, never as success.
  Proven by `Incomplete_response_reports_error_not_success`,
  `Empty_response_is_error`.
- Client counts deliberately exclude `client_type=1` (ServerQuery clients), so the number
  reflects real voice users.

## What is **not** verified, and must be before production

Honest limits of this environment:

1. **No real TeamSpeak server binary was available**, so no test was run against it.
   Everything process-related was tested against `tests/MockServer`, which mimics process
   behaviour but is not TeamSpeak.
2. **ServerQuery command behaviour was not replayed against a live server.** The commands
   used (`login`, `serverinfo`, `clientlist`) follow the documented protocol and the error
   codes, and the parser is tested against fixtures — but the actual server-side field
   names and responses were not observed first-hand.
3. **No Cloudflare deployment was performed.** No account, no token, no live traffic.
   The `wrangler.jsonc` still contains the placeholder D1 id and `scripts/deploy.ps1`
   will actively refuse to deploy until that is replaced.

## Known limitations

- `SecureCredentialStore` writes the whole secret blob on every change. With few keys this
  is fine; it would not scale to thousands of entries.
- The DPAPI path relies on the same Windows user. Copying `secrets.bin` to another
  Windows user on the same machine will not decrypt (by design) and is detected as
  corrupt.
- No attempt is made to hide the app from a local administrator, who can always read the
  DPAPI blob of any user in their session. DPAPI protects against other users and against
  the file being copied off the machine, not against a local admin.
- Binary signing is not set up. A self-contained, unsigned EXE will trip SmartScreen on
  first run. Code-sign with a certificate to avoid this; no key material is in this repo.
